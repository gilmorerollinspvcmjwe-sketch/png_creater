# Atlas 对象配置驱动 UI 升级设计

**日期：** 2026-04-01

## 目标

在当前 `atlas` UI 基线上，把后续 100+ 个 CRM 页面升级路线确定为：

- 固定页面模式
- 前端对象配置驱动
- 受限的通用组件槽位复用

这次不是继续逐页手工换皮，也不是做一个无限灵活的低代码引擎，而是做一套“产品可维护、开发可扩展、后续可对接后端”的对象工作台 UI 基础设施。

## 已确认前提

- 后续页面主要复用现有这 100+ 个页面，不新增全新的页面类型
- 当前阶段仍然是纯前端项目，配置先写在前端代码中
- 后端接口对接放到后续阶段逐步处理
- 需要支持自定义对象
- 需要支持自定义字段
- 每个对象允许配置：
  - 列表列
  - 详情分组
  - 表单分组
  - 关联区块
- 页面模式存在明确边界：
  - 详情页固定左中右三栏
  - 列表页以标准列表工作台为主，只替换字段和局部动作
  - 表单页只允许标准分组与字段渲染
- 配置最终是给产品维护，不是只给开发维护
- 项目里已经有原始业务设计，本次重点是 UI 语法升级，不是业务重设计

## 核心设计结论

后续工作不再以“继续补更多通用组件”为主，而要切换成“固定骨架 + 对象配置 + 字段渲染协议”的路线。

这意味着：

1. 页面布局语法固定
2. 页面中的业务内容由对象配置决定
3. 字段展示与编辑由统一字段类型协议决定
4. 真正的对象差异通过配置表达，不通过复制页面结构表达

最重要的取舍是：

- 不走“每个对象自己写一套页面”的路线
- 不走“任何页面都可任意拼装”的路线
- 只走“在固定页面模式内允许对象配置差异”的路线

这是当前项目最适合支撑 100+ 页面 UI 升级的方案。

## 为什么不继续只做组件库扩张

如果继续按当前思路不断补通用按钮、标签、卡片、占位块，短期会显得更整洁，但 100+ 页面升级依然会落回下面的问题：

- 页面依然要手工装配
- 对象差异依然写在 JSX 里
- 自定义字段一多就会导致条件分支膨胀
- 产品无法真正维护对象差异，只能继续依赖开发改页面

所以后续重点应该从“抽更多基础组件”切换为“抽稳定页面模式 + 设计对象配置结构”。

组件仍然要抽，但要服务配置驱动，不是为了组件数量增长。

## 总体架构

后续 UI 升级采用 4 层结构：

1. 页面骨架层
2. 区块层
3. 字段渲染层
4. 对象配置层

这 4 层共同约束后续 100+ 页面如何生成。

### 1. 页面骨架层

这一层负责固定页面的大结构，不允许对象突破：

- `AtlasListShell`
- `AtlasDetailShell`
- `AtlasPreviewDrawerShell`
- `AtlasDrawerShell`
- `AtlasDangerModalShell`

职责是统一：

- 页面标题区
- 命令区
- 列表主体区
- 预览抽屉
- 三栏详情结构
- 表单抽屉
- 危险操作弹层

对象层不能改变这些骨架的根布局，只能填充内容槽位。

### 2. 区块层

这一层负责固定 CRM 工作台中的标准业务区块。

建议逐步稳定为以下块：

- `AtlasIdentityRail`
- `AtlasMetricStrip`
- `AtlasTabWorkspace`
- `AtlasPropertyGroup`
- `AtlasAssociationSection`
- `AtlasActivitySection`
- `AtlasFormSection`
- `AtlasActionCluster`

这些区块是对象配置真正作用的落点。

对象可决定显示哪些区块、顺序如何、每个区块内出现哪些字段，但不能发明新的根布局系统。

### 3. 字段渲染层

这一层负责把字段定义渲染到不同场景中：

- 列表单元格
- 详情字段项
- 表单编辑器
- 预览摘要项
- 关联对象摘要项

字段渲染层要统一字段类型和表现协议，否则对象配置会很快失控。

### 4. 对象配置层

这一层定义每个对象在固定页面模式下的差异化内容。

对象配置应集中在前端 schema 文件中，而不是散落在页面组件内部。

每个对象只需要通过配置描述：

- 这个对象有哪些字段
- 列表页显示哪些列
- 详情页中栏有哪些分组
- 表单有哪些分组和编辑字段
- 右栏有哪些关联区块
- 主标题、副标题、状态字段分别是什么
- 默认动作和局部动作是什么

## 页面模式边界

这是本方案最重要的约束，必须写死。

### 列表页边界

列表页永远是标准列表工作台，不允许对象自定义成全新结构。

固定部分：

- 页面头部
- 命令栏
- 筛选摘要
- 列表主体
- 行操作
- 页脚或状态区
- 可选预览抽屉

允许配置的部分：

- 列表列
- 默认排序
- 可筛选字段
- 行操作集合
- 批量操作集合
- 顶部主操作
- 预览抽屉中显示的摘要字段

明确不允许：

- 某个对象自定义完全不同的列表页面布局
- 某个对象自定义独立 KPI 大屏语法作为默认列表
- 列表页为单个对象发明新的骨架组件

### 详情页边界

详情页永远固定为左中右三栏。

左栏固定承担：

- 身份摘要
- 关键状态
- 主动作
- 少量关键指标

中栏固定承担：

- tab 工作区
- 主字段分组
- 长文本或业务正文
- 活动或历史内容

右栏固定承担：

- 关联对象
- 关联摘要
- 工作流辅助信息

允许配置的部分：

- 左栏显示哪些关键字段
- 中栏有哪些 tab
- 每个 tab 下有哪些字段组或业务块
- 右栏显示哪些关联区块

明确不允许：

- 某个对象改成双栏或四栏
- 某个对象把解释性说明卡堆满右栏
- 某个对象重新定义详情页主骨架

### 表单页边界

表单统一使用抽屉模式。

允许配置：

- 表单分组
- 字段顺序
- 字段可编辑性
- 校验规则
- 某些字段的条件显隐

明确不允许：

- 某个对象自定义一整套专属表单布局系统
- 为单个对象额外发明复杂向导式流程，除非后续单独立项

### 关联区边界

右栏关联区必须标准化。

建议只允许几种固定关联区块：

- 关联对象列表
- 关联记录摘要
- 最近活动
- 下一步动作
- 工作流提示

对象可以配置区块顺序和字段，但不能自由拼装任意卡片系统。

## 对象配置模型

为了让产品可维护，对象配置不能过于程序化，也不能分散在多个页面文件中。

建议每个对象有一份集中配置，例如：

- `objectMeta`
- `fieldMeta`
- `listSchema`
- `detailSchema`
- `formSchema`
- `associationSchema`
- `actionSchema`

### 对象定义

对象定义至少包含：

- `objectKey`
- `label`
- `labelPlural`
- `icon`
- `primaryField`
- `secondaryField`
- `statusField`
- `ownerField`
- `defaultSort`
- `supports`

作用是确定这个对象的通用身份语义。

### 字段定义

字段定义至少包含：

- `key`
- `label`
- `type`
- `required`
- `readonly`
- `sortable`
- `filterable`
- `searchable`
- `listVisible`
- `detailVisible`
- `formVisible`
- `relation`
- `display`

字段定义负责回答两个问题：

1. 这个字段是什么
2. 这个字段在不同页面里能不能出现

### 列表 schema

列表 schema 负责定义：

- 显示哪些列
- 列顺序
- 哪些列可排序
- 哪些字段出现在筛选器
- 哪些动作出现在行尾
- 哪些字段进入预览抽屉

列表 schema 不负责定义页面根布局。

### 详情 schema

详情 schema 负责定义：

- 左栏显示哪些身份字段和指标
- 中栏有哪些 tab
- 每个 tab 下有哪些字段组
- 每个字段组的标题、顺序、字段集合
- 右栏有哪些关联区块

详情 schema 的能力重点是“内容分组”，不是“布局发明”。

### 表单 schema

表单 schema 负责定义：

- 表单分组
- 每组字段顺序
- 字段编辑器类型
- 校验规则
- 创建态与编辑态差异

表单 schema 必须让产品可以理解，但不应该复杂到像流程编排系统。

### 关联 schema

关联 schema 负责定义：

- 哪些关联对象显示在右栏
- 区块顺序
- 每个区块展示几条记录
- 每条关联记录显示哪些摘要字段
- 是否展示快速新建或跳转动作

## 字段类型协议

为了让自定义字段真正可复用，字段类型必须先规范。

首批建议固定支持：

- `text`
- `textarea`
- `number`
- `money`
- `date`
- `datetime`
- `select`
- `multiSelect`
- `status`
- `boolean`
- `tag`
- `user`
- `email`
- `phone`
- `relation`
- `avatar`

每种字段类型都需要同时定义三种渲染方式：

1. 列表页如何显示
2. 详情页如何显示
3. 表单里如何编辑

这样后续新增字段，只需要补字段定义，不需要重写页面。

## 组件抽象策略

后续仍然需要抽组件，但策略要变。

### 应该继续抽的组件

优先抽高复用、稳定语法组件：

- 页面骨架组件
- 标准业务区块组件
- 字段渲染器
- 动作区组件
- 关联区组件

这些组件会直接被 100+ 页面复用。

### 不应该过度抽的组件

不建议继续大量抽两类东西：

- 单对象专属视觉块
- 纯包装型小组件

如果一个组件只在单个对象里成立，或者只是减少几行 JSX，并没有形成稳定协议，就应该留在对象装配层里。

## 产品维护原则

因为对象配置要给产品维护，所以必须控制配置难度。

配置设计要满足：

- 尽量接近业务语言
- 避免出现大量 UI 细节参数
- 不要求产品理解 React 组件结构
- 不要求产品维护布局逻辑

产品应该改的是：

- 列表列
- 分组标题
- 字段顺序
- 哪些字段出现
- 关联区显示哪些内容

产品不应该改的是：

- 页面整体布局
- 组件内部实现逻辑
- 样式细节
- 渲染器内部协议

## 与后端对接的兼容边界

当前配置先写前端，但结构必须能平滑过渡到后端。

所以对象配置现在虽然放在前端，也要尽量保持后续可序列化。

这意味着：

- 配置尽量使用纯数据结构
- 避免把大量 JSX 直接写入 schema
- 避免在 schema 中塞入不可序列化的复杂函数
- 特殊渲染能力通过受控 renderer key 映射

当前阶段允许少量前端映射层存在，但不能让 schema 强依赖页面代码。

## 实施范围

### 本次后续升级应该做的事

- 补齐页面骨架层
- 固化字段类型协议
- 建立对象配置 schema
- 把现有五类对象页逐步迁到配置驱动结构
- 为后续 100+ 页面复用打基础

### 当前不应该做的事

- 不做无限灵活的页面搭建系统
- 不做对象可自由改变根布局
- 不把 schema 设计成低代码平台
- 不为了“通用”而一次性抽空所有对象专属逻辑

## 推荐实施顺序

推荐按下面顺序推进：

1. 先补齐 `AtlasListShell / AtlasDrawerShell / AtlasDangerModalShell`
2. 再稳定 `IdentityRail / PropertyGroup / FormSection / AssociationSection / TabWorkspace`
3. 建立统一字段类型与字段渲染协议
4. 建立对象配置 schema
5. 先把现有五对象迁成“骨架固定 + 配置驱动”
6. 再用这套结构去承接后续 100+ 页面

## 成功标准

当以下条件成立时，可以认为路线正确：

- 新页面升级不再依赖逐页手工拼 UI
- 新对象主要通过配置接入，而不是复制页面文件
- 自定义字段新增时不需要改页面骨架
- 产品可以维护对象级展示差异
- 开发只需要补通用槽位和渲染协议，不需要反复重写对象页
- 后续对接后端时，可以把前端 schema 逐步替换为接口返回配置

## 结论

后续 100+ 页面 UI 升级，应该继续抽组件，但抽象目标必须改变：

- 不是继续堆更多零散基础组件
- 而是优先固定页面模式、区块协议和字段渲染协议
- 再让对象通过前端配置去复用这些能力

一句话总结就是：

后续路线应当是“受限配置驱动的对象工作台”，而不是“继续手工改页面”或“做无限灵活的低代码系统”。
